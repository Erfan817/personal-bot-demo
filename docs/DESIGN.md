# 设计笔记

这份文档记录**每个设计决策背后的「为什么」**，以及**已知的取舍和局限**。
代码能看出"做了什么"，这份文档解释"为什么这么做"。

---

## 一、三条设计原则

### 1. 分层要有明确边界，每层只解决一类问题

判断分层是否合格的唯一标准：**换掉某一层，其他层要不要改？**

| 换什么 | 实际要改哪些文件 |
|---|---|
| 换 agent 框架（手写循环 → pi-agent-core） | `brain/` 两个文件。**渠道层、总线一行没改** |
| 换渠道（命令行 → 飞书） | `channels/` 加一个文件 + `index.mjs` 一行 |
| 换模型（DeepSeek → Kimi） | `.env` 一行 |
| 加工具 | `tools/` 两个文件 |
| 加定时任务 | `scheduler/jobs.mjs` 一行 |

**如果换一层要动三个地方，说明边界画错了。**

### 2. 数据跨层传递要用「窄接口」，不要传整个对象

- 渠道 → 大脑：`{ chatId, text }`，不是飞书的事件对象
- 大脑 → 渠道：`emit("answer", "纯文本")`，不是框架的消息对象
- 工具 → 大脑：`{ content: [{type:"text", text}] }`，框架规定的格式

**为什么**：传整个对象意味着下层要了解上层的内部结构，耦合就产生了。
**我们踩过这个坑**（见"踩坑记录 ③"）：把简化对象塞回框架，框架静默丢弃 → 空回答。

### 3. 从日志里自助获取配置，而不是让人去后台查

白名单为空时，不是"允许所有人"，而是**"拒绝所有人 + 打印你的 open_id"**。

- **安全默认**：还没配好之前，不会裸奔
- **自助引导**：不用去平台后台翻 ID，发条消息它自己告诉你

**同一个模式可以推广到任何"需要填 ID/Token"的地方。**

## 二、各层的边界

### 协议层 `channels/`

**只做两件事**：把外部消息翻译成内部格式、把内部结果翻译成外部格式。

**不该做的事**：
- ❌ 不该判断"这个人能不能用"（那是桥接层）
- ❌ 不该决定"要不要记住"（那是记忆层）
- ❌ 不该写业务逻辑

**飞书渠道的特殊约束**：3 秒超时。这**不是业务逻辑**，是飞书的平台规则，所以它属于协议层的职责——协议层负责适配平台的怪癖。

### 桥接层 `gateway/`

**消息进大脑之前、出大脑之后的所有关卡。**

| 模块 | 职责 | 失败时的行为 |
|---|---|---|
| `access` | 谁能让 bot 干活 | 静默丢弃 |
| `dedupe` | 同一条消息只处理一次 | 静默丢弃 |
| `ratelimit` | 防止被刷爆 | **回复提示**（用户需要知道） |
| `outbound` | 长回复切分 | — |

**为什么"静默"和"提示"要分开**：陌生人发消息，回复他等于告诉他"这个 bot 存在"；而限频是针对**自己人**的，必须让他知道。

### 大脑层 `brain/`

**只负责循环，不负责展示。**

分割线很清晰：
- ✅ 组装 Agent（模型、工具、提示词）
- ✅ 挂白名单闸门
- ✅ 把框架事件翻译成渠道事件
- ✅ 跑前载入历史、跑后落盘
- ❌ 不打印任何东西

**为什么历史要拼进 system prompt 而不是 messages**：见"踩坑记录 ③"。
代价是历史以"参考资料"身份出现，不是严格的多轮对话——**这个取舍是有意的**：
换来的是「不依赖框架内部格式」，也就意味着**换框架时这层不用重写**。

### 工具层 `tools/`

**能力白名单的唯一入口。**

设计要点：
- **注册表模式**：想加工具只能改 `index.mjs`
- **双重验证**：框架级 `beforeToolCall` 闸门 + 每个工具自己的输入校验
- **失败要 throw，不要返回错误文本**：框架会把 throw 转成 `isError: true` 的 toolResult 给模型

**为什么要有第二道（工具自己的校验）**：
`beforeToolCall` 只能判断"这个名字在不在白名单"，判断不了"这个参数危不危险"。
模型可能被骗（prompt injection）后传入恶意参数——**工具自己的校验是最后一道防线**。

```javascript
// calc 里的例子：即使模型被骗，也执行不了危险输入
if (!/^[0-9+\-*/(). ]+$/.test(expr)) {
  throw new Error("表达式含非法字符");
}
```

### 记忆层 `memory/`

**两个不同的东西，分开实现**：

| | 会话历史 | 长期记忆 |
|---|---|---|
| 存哪 | `messages` 表 | 同一张表 |
| 怎么用 | **自动载入最近 N 条**进上下文 | **agent 主动调 `history_search`** |
| 解决 | "刚才那个时间加一小时" | "我上次跟你说的事" |

**中文分词的坑**：FTS5 默认的 `unicode61` 分词器按"非字母数字"切词，中文整句会变成一个 token，检索基本失效。
**解法**：`tokenize='trigram'`（按 3 字符滑窗），代价是查询串必须 ≥3 字符才走 FTS。

### 调度层 `scheduler/`

**从"你问它答"到"它主动找你"。**

关键设计：**`deliver` 事件和 `answer` 事件分开**。

| 事件 | 目标 | 用途 |
|---|---|---|
| `answer` | "当前正在说话的那个人" | 被动回答 |
| `deliver` | **显式指定的 chatId** | 主动推送 |

**为什么不复用**：被动回答需要知道"谁在问"（一个隐含的全局状态），主动推送自带目标。
混在一起会让渠道层去猜——**那是 bug 的温床**。

**cron 解析里的经典陷阱**：「日」和「周」是**或**关系，但只在**两个都被限制**时才是。
如果无脑写 `dom.has(d) || dow.has(d)`，那么配 `0 9 15 * *`（每月 15 号）时，
`dow` 是 `*` 全匹配 → 结果永远为真 → **每天都触发**。

## 三、一条消息的完整旅程

```
📱 用户在飞书说："帮我查一下 Node.js 最新版本"

① channels/feishu.mjs
   收到 WebSocket 事件 → 解析出 { chatId, openId, text, messageId }
   ⚠️ 必须在 3 秒内返回，所以只做解析

② gateway/index.mjs  admit()
   ① 准入：openId 在白名单里吗？不在 → 静默丢弃
   ② 幂等：messageId 见过吗？见过 → 静默丢弃
   ③ 限频：令牌桶还有令牌吗？没有 → 回复"太频繁了"

③ 入队，立刻 return                ← 让 SDK 去 ACK 飞书
   后台 worker 取出来跑

④ brain/loop.mjs
   载入该 chatId 最近 20 条历史 → 拼进 system prompt
   创建 Agent（模型 + 5 个工具 + beforeToolCall 闸门）

⑤ agent 循环（框架负责）
   turn 1: 模型要调 web_search("Node.js 最新版本")
           → beforeToolCall 检查：web_search 在白名单 ✅
           → 执行 → 结果回灌
   turn 2: 模型要调 web_fetch("https://nodejs.org/en/")
           → 白名单 ✅ → 执行 → 结果回灌
   turn 3: 模型不再要工具 → 产出最终回答
   ⚠️ 每一轮都检查 shouldStopAfterTurn（死循环保护）

⑥ events.mjs
   框架事件 → 翻译成我们的 step / tool_call / answer 事件

⑦ channels/feishu.mjs
   订阅了 answer → 拼上工具日志 → gateway/outbound 切分 → 发飞书

⑧ memory/messages.mjs
   saveMessage(chatId, "user", 用户原话)
   saveMessage(chatId, "assistant", 最终回答)
```

**注意 ③ 那个"立刻 return"**——它同时解决了两件事：
满足飞书的 3 秒要求，以及让长任务不阻塞消息接收。

## 四、已知局限

| 局限 | 影响 | 改进方向 |
|---|---|---|
| **单用户信任模型** | 多用户共享一个 Agent，工具权限也共享 | 按用户隔离会话与工具策略；敌对用户要拆成独立实例 |
| **记忆是字面检索，无语义召回** | 同义改写 / 口语换词召不回（「宠物」找不到「橘猫」）；查询 <3 字降级 LIKE 全表扫 | 加 embedding + 混合排序；边界已在 `tests/memory.test.mjs` 固化 |
| **历史塞 system prompt** | 不是严格的多轮对话，模型可能把它当"参考资料" | 用框架自带的会话存储（`pi-session-backend-sqlite-node`） |
| **串行处理消息** | 一次只能跑一个任务，排队等待 | 加并发 worker + 按 chatId 分队列 |
| **无流式输出** | 用户要等全部生成完才看到回复 | 订阅 `message_update` 事件，做飞书"打字机"效果 |
| **记忆无衰减/遗忘** | 库会无限增长，检索质量会下降 | 加时间衰减、容量上限、重要度评分 |
| **网搜索依赖 DuckDuckGo** | 数据中心 IP 可能被人机验证拦 | 检测已做（不会误报"没搜到"）；配 `BRAVE_API_KEY` 走 API |
| **告警只在本机** | 出事时人不在电脑前不知道 | 写 `data/ALERT` + journal；外部告警通道待做 |
| **无端到端集成测试** | 飞书通道靠人工验证 | 单元测试覆盖纯逻辑层；集成测试待补 |
| **无用量统计** | 不知道花了多少钱 | 记录 token 消耗，做成本看板 |
| **单机无冗余** | 服务器挂了服务就断了 | 目前接受（个人用途） |

## 五、如果要重写一遍

按"最该先做什么"排序：

1. **先写 echo bot 打通协议层** —— 平台配置（权限、事件订阅、鉴权）是最容易卡住的地方，
   先把它啃掉，后面全是纯逻辑
2. **再写 agent 循环（手写一遍）** —— 理解循环本身，之后用框架才知道框架帮你省了什么
3. **然后立刻上桥接层** —— 不要等到"功能做完再加安全"。有工具能力的 bot 一上线就该有闸门
4. **记忆层最后做** —— 它最复杂，但前三层跑通后它才有意义
5. **运维要提前** —— `systemd` 应该在第一次"关掉终端 bot 就死了"之后就做，不要拖

**最不该做的**：一上来就设计完美的分层。**我们的分层是被需求推着长出来的**
（加飞书 → 发现要解耦渠道；加定时推送 → 发现要区分 answer/deliver）。
**先跑通，再重构，每一层的出现都有具体理由。**

## 六、值得反复用的几个模式

| 模式 | 用在哪 | 本质 |
|---|---|---|
| **事件总线解耦** | `events.mjs` | 生产者不知道消费者是谁 |
| **注册表白名单** | `tools/index.mjs` | 能力的唯一入口，加能力只能改一处 |
| **钩子式闸门** | `beforeToolCall` | 在框架的执行路径上插一道，而不是在业务代码里到处查 |
| **安全默认 + 自助引导** | 空白名单拒绝所有人 + 打印 open_id | 默认安全，配置值自己找上门 |
| **心跳判定假活** | `heartbeat.mjs` + `healthcheck.sh` | 用状态判断健康不可靠，要让它自己证明还活着 |
| **区分"没有数据"和"拿不到数据"** | DDG 验证页检测 | 两者给用户的建议完全不同 |
| **无副作用检查在前** | 准入 → 幂等 → 限频 | 便宜的、不改状态的先做 |
| **窄接口跨层** | `{chatId, text}` / `emit("answer", 字符串)` | 不传整个对象，避免下层了解上层内部结构 |
